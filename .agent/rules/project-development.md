# Project Development Rules

## Purpose

These rules define project-specific development conventions for frontend, backend, database, APIs, configuration, internationalization, security, logging, migrations, authorization, styling, and shared architecture.

These rules apply whenever code is created, modified, refactored, reviewed, migrated, integrated, or generated by an AI coding agent.

Always inspect the existing implementation before introducing a new pattern. Do not create a second way of solving a problem when the codebase already has an established approach.

---

# 1. General Development Rules

## 1.1 Read Existing Code First

Before implementing a feature, inspect the relevant module, controller, service, DTO, entity, migration, API endpoint, hook, component, configuration, permission, translation, and tests.

Prefer extending existing patterns over inventing new ones.

## 1.2 Code Must Be Readable

Code must be easy to understand without unnecessary mental effort.

Prefer meaningful names, explicit logic, simple functions, predictable behavior, clear responsibilities, and consistent patterns.

Avoid clever shortcuts, cryptic expressions, excessive nesting, unnecessary abstractions, and duplicated logic.

## 1.3 Maintain Consistency

Follow existing project conventions for naming, casing, directory structure, services, controllers, DTOs, entities, hooks, endpoints, components, logging, error handling, styling, configuration, permissions, translations, and migrations.

Consistency is more important than personal preference.

## 1.4 Prefer Existing Implementations

Before creating a new helper, utility, component, hook, DTO, service, entity, enum, constant, validator, or API abstraction, search the codebase first.

Reuse or extend existing code when appropriate. Do not duplicate existing functionality.

---

# 2. Naming and Readability

## 2.1 Use Meaningful Names

Always use meaningful names for variables, constants, functions, methods, classes, DTOs, entities, hooks, React components, files, directories, enums, enum members, and database fields.

Avoid vague names such as `data`, `value`, `result`, `temp`, `x`, `item`, or `thing` when a more descriptive name is possible.

Prefer names such as:

```ts
activeComplaints
authenticatedUser
selectedReportVersion
approvalResult
```

## 2.2 Maintain Consistent Case

Follow the project convention consistently.

Use `camelCase` for variables, functions, and methods.

Use `PascalCase` for classes, DTOs, entities, components, interfaces, and types.

Use `UPPER_SNAKE_CASE` for true constants where already used in the project.

For database names, follow the existing database naming convention consistently.

Do not randomly mix camelCase, snake_case, and PascalCase.

---

# 3. Functions

## 3.1 Keep Functions Simple

Make functions as simple as practical after satisfying correctness, security, validation, error handling, and business requirements.

Do not simplify by removing necessary checks.

## 3.2 Use Meaningful Function Names

Function names must describe what the function actually does.

Avoid vague names such as:

```ts
process()
handle()
execute()
run()
doStuff()
```

Prefer:

```ts
approveComplaint()
generateReport()
validateSubmission()
assignReviewer()
```

## 3.3 Keep Functions Focused

A function should have one clear responsibility.

Avoid combining unrelated validation, persistence, notification, formatting, authorization, and external API calls.

Split functions when it improves clarity, but do not over-split small coherent logic.

---

# 4. Internationalization

## 4.1 Do Not Hardcode User-Facing Text

Always use i18n for user-facing text.

This includes labels, buttons, headings, dialogs, validation messages, notifications, error messages, success messages, warnings, and backend messages shown to frontend users.

Do not hardcode text directly in frontend or backend responses.

## 4.2 Do Not Use i18n Default Values

Do not use translation fallbacks such as:

```ts
t('user.notFound', 'User not found')
```

or:

```ts
defaultValue: 'User not found'
```

The translation key must exist explicitly. Fallback values can hide missing translations.

## 4.3 Add Translation Keys Properly

When introducing a translation key:

- add it to all required translation files
- follow existing namespaces
- follow existing naming conventions
- update all supported languages required by the project

Do not add a translation key in code without adding its actual translation.

## 4.4 Backend Errors Must Use i18n

Any backend message intended for frontend display must use the backend i18n setup.

Do not return hardcoded English messages when the message is user-facing.

---

# 5. Fallback Values

## 5.1 Avoid Unnecessary Fallbacks

Do not mask missing or incorrect data using arbitrary fallback values.

Avoid:

```ts
const username = user.name || 'Unknown';
```

when `user.name` should exist.

Instead:

1. determine where the correct value should come from
2. fix the source
3. validate the value
4. handle genuine optional cases explicitly

## 5.2 Do Not Use Fallbacks to Silence Type Problems

Avoid:

```ts
value ?? ''
value || []
```

merely to satisfy TypeScript or avoid runtime errors.

Understand why the value is absent first.

---

# 6. Enums and Constants

## 6.1 Use Enums Properly

Use enums for defined value sets such as statuses, types, workflow states, roles, permissions, and report types.

Avoid scattered magic strings.

Prefer:

```ts
status === UserStatus.ACTIVE
```

instead of:

```ts
status === 'ACTIVE'
```

## 6.2 Reuse Existing Enums

Do not create duplicate enums for the same concept. Search existing code first.

## 6.3 Avoid Magic Values

Use enums, named constants, and configuration values instead of scattered unexplained strings or numbers.

---

# 7. Backend Validation

## 7.1 Backend Validation Is Mandatory

Never rely only on frontend validation.

All untrusted input must be validated in the backend.

Frontend validation is for UX. Backend validation enforces correctness and security.

## 7.2 Prefer DTO Validation

Use DTOs wherever appropriate for request bodies, query parameters, path parameters, and service inputs.

Use the existing validation framework.

## 7.3 Validate Business Rules in Services

DTO validation handles input structure.

Services or domain logic must enforce business rules such as valid status transitions, ownership, relationships, availability, limits, permissions, and required state.

---

# 8. Controllers

## 8.1 Keep Controllers Thin

Controllers should primarily:

1. receive requests
2. validate/transform input
3. apply authorization where appropriate
4. call services
5. return responses

## 8.2 Do Not Put Service Logic in Controllers

Do not create service functions inside controllers.

Avoid putting database logic, workflow logic, report processing, large transformations, notification orchestration, or complex calculations inside controllers.

## 8.3 Split Controllers Only When Necessary

Separate controllers where there is a clear responsibility boundary.

Do not create unnecessary controller fragmentation.

## 8.4 Do Not Split Applications Unless Explicitly Requested

Do not create new backend apps, microservices, or frontend apps unless explicitly requested.

Prefer extending the existing application architecture.

---

# 9. Services

## 9.1 Split Services by Responsibility

Separate services when there is a meaningful functional boundary.

For example:

```text
ComplaintService
ComplaintReportService
ComplaintNotificationService
```

may be justified when each has substantial independent behavior.

## 9.2 Do Not Over-Split Services

Do not create excessive services simply to reduce file size.

Avoid unnecessary fragmentation such as separate create/read/update/delete services for simple CRUD unless domain complexity requires it.

---

# 10. TypeORM Entities

## 10.1 Follow Existing TypeORM Conventions

Use the project's existing base entity, ID conventions, timestamp handling, relationships, indexes, constraints, and inheritance patterns.

Do not create a separate persistence style.

## 10.2 Reuse Entity Inheritance

If common fields already exist in a base entity, use that inheritance structure.

Do not duplicate fields unnecessarily.

## 10.3 Register New Entities

When adding an entity:

1. create the entity
2. add it to the appropriate entity collection
3. add it to `db.entities.const`
4. ensure it is loaded through `db.config.module.ts`

Follow the existing project implementation exactly.

---

# 11. Migrations

## 11.1 Synchronization Is Not a Replacement for Migrations

When TypeORM synchronization is disabled:

```text
synchronize = false
```

every schema change requires a migration.

## 11.2 Generate Migrations Using Commands

Do not manually create migrations first when TypeORM can generate the schema difference.

Use the existing project migration generation command.

Example conceptually:

```bash
typeorm migration:generate ...
```

Use the actual command defined in the repository.

## 11.3 Always Review Generated Migrations

Inspect generated migrations before accepting them.

Check intended columns, unintended deletions, table recreation, indexes, constraints, foreign keys, and rollback behavior.

Do not blindly trust generated migrations.

## 11.4 Keep Migrations Readable

Migration intent should be understandable.

Generated migrations may be cleaned for readability where safe.

Do not modify them in a way that changes correctness unintentionally.

## 11.5 Every Entity Schema Change Requires a Migration

This includes:

- new entity
- new column
- removed column
- changed type
- nullability changes
- relationship changes
- indexes
- constraints
- enum changes

## 11.6 Do Not Rewrite Applied Migrations

Once a migration has been used in shared environments, do not edit it.

Create a new migration instead.

---

# 12. Frontend API Structure

## 12.1 Maintain Endpoints Centrally

Keep endpoints in:

```text
api/endpoints/
```

Do not hardcode endpoint strings inside components.

## 12.2 Use the Existing Fetcher

Use the project's existing `fetcher`.

Do not introduce random `fetch(...)` or `axios(...)` calls when the project already has a request abstraction.

## 12.3 Use the Existing Service Layer

API operations should be placed in the appropriate frontend service layer.

Do not perform raw HTTP calls directly inside UI components.

## 12.4 Use TanStack Query

Use TanStack Query following the existing hooks directory patterns.

Use it for fetching, mutations, caching, loading state, refetching, and invalidation.

Do not build a parallel server-state solution.

## 12.5 Keep Query Keys Consistent

Use existing query-key conventions or factories.

Do not create inconsistent query keys for the same resource.

## 12.6 Handle Mutations Correctly

After mutations:

- invalidate relevant queries
- update cache where appropriate
- avoid unnecessarily invalidating unrelated queries

Do not leave stale UI state after successful mutations.

---

# 13. React State

## 13.1 Use Local State for Local UI State

Do not move local state into global Context unnecessarily.

## 13.2 Use React Context for True Global Client State

React Context may be appropriate for theme, authenticated user metadata, global preferences, and app-wide selections.

## 13.3 Do Not Duplicate Server State Into Context

If state comes from the backend and is already managed by TanStack Query, do not duplicate it into Context without a real reason.

TanStack Query should remain the source of truth for server state.

## 13.4 Use localStorage Carefully

Use localStorage only when persistence across refreshes is required.

Do not store passwords, secrets, sensitive tokens, or sensitive personal data without explicit architectural approval.

---

# 14. Frontend Components

## 14.1 Prefer Existing Components

Always inspect the existing component set first.

Use existing project wrappers before creating new components.

## 14.2 Ant Design Is the Main Component Library

Use Ant Design where appropriate.

Prefer existing project wrappers around Ant Design components.

## 14.3 Create Wrappers Only When They Add Value

Wrappers may standardize theme, styling, validation, accessibility, loading behavior, permissions, or common props.

Do not create wrappers that only forward props without adding value.

## 14.4 Use `renderField` Where It Helps

Use generic `renderField` for repetitive field rendering where it clearly reduces duplication.

Do not force every field into it.

Complex or domain-specific fields may be clearer as dedicated components.

## 14.5 Component Placement

If a component contains domain-specific logic, keep it near the related module/page.

If a component is generic, reusable, and domain-independent, place it in the global components directory.

## 14.6 Build Components for Real Reuse

Reusable components should be readable, responsive, accessible, extensible, and predictable.

Do not create speculative reusable components before a real reusable concept exists.

---

# 15. Layouts and Routes

## 15.1 Use Existing Layouts

Pages must reuse existing layouts.

Do not recreate headers, sidebars, common navigation, or global containers inside individual pages.

## 15.2 Follow Existing Route Patterns

Define routes using the existing routing structure.

Maintain consistency for nesting, permissions, layouts, lazy loading, and route naming.

---

# 16. Styling

## 16.1 Prefer Tailwind CSS

Avoid inline styling for ordinary styling.

Prefer the project's Tailwind conventions.

## 16.2 Do Not Hardcode Colors

Prefer ThemeContext, theme variables, CSS variables, Ant Design tokens, or Tailwind theme configuration.

## 16.3 Maintain Theme Compatibility

New UI must work with supported themes.

Do not assume a fixed background or text color.

## 16.4 Reuse Styles Where Appropriate

Reuse theme tokens, utilities, wrapper components, and shared style definitions when styles genuinely repeat.

## 16.5 Style Overrides Are Allowed When Necessary

When overriding library styles, follow the existing override strategy, keep overrides scoped, and avoid unnecessary global CSS hacks.

---

# 17. Responsiveness

## 17.1 Maintain Mobile Responsiveness

New UI must be considered for desktop, tablet, and mobile.

## 17.2 Check Common Responsive Problems

Review forms, tables, modals, long labels, translated strings, buttons, navigation, and horizontal overflow.

---

# 18. Frontend Validation

Frontend validation should provide good UX.

Use relevant required checks, format checks, length checks, and field relationship validation.

Frontend validation never replaces backend validation.

---

# 19. Authentication and Authorization

## 19.1 Use Existing Authentication

Do not create a second authentication mechanism.

Use the existing project setup.

## 19.2 Prefer Permissions Over Hardcoded Roles

Prefer permission checks over hardcoded role comparisons unless role-specific behavior is explicitly required.

## 19.3 Do Not Hardcode Role Strings

Use existing enums/constants.

## 19.4 Authorization Must Be Enforced in Backend

Frontend permission checks are UX only.

Backend checks are the actual security boundary.

## 19.5 Add Permission Checks With New Features

When implementing a feature, explicitly determine who may view, create, update, delete, approve, and administer.

Do not leave new endpoints accidentally unprotected.

---

# 20. Rate Limiting

Use the project's existing rate-limiting implementation.

Do not introduce another mechanism.

Use it where appropriate, especially for authentication, password recovery, OTP, public forms, expensive endpoints, and externally exposed operations.

---

# 21. Time and Time Zones

## 21.1 Store Absolute Times as UTC

Absolute timestamps should follow the project's UTC epoch convention.

## 21.2 Pass UTC Epochs for Absolute Times

Prefer UTC epoch values between frontend and backend for absolute moments.

Avoid ambiguous local date-time strings.

## 21.3 Convert for Presentation

Convert UTC values into the user's timezone where display or local business interpretation requires it.

## 21.4 Use the Existing Timezone Header

Use the timezone header already passed by the application.

Do not introduce a second timezone mechanism.

## 21.5 Do Not Depend on Server Local Time

Business logic must not assume the server's timezone.

## 21.6 Distinguish Date Types

Do not blindly convert every date into an epoch.

Differentiate absolute instants, date-only values, local wall-clock time, and timezone-aware datetime.

A birthday or date-only business field may not belong as an epoch.

---

# 22. Configuration

## 22.1 Move Configurable Values to Configuration

Environment-dependent values should use the existing configuration mechanism.

Examples include API hosts, feature flags, external URLs, environment identifiers, and environment-specific timeouts.

## 22.2 Use `.env` Only for Real Environment Configuration

Do not move ordinary application constants into `.env` unnecessarily.

## 22.3 Update `.env.develop` When Needed

When adding a required environment variable:

- update the appropriate development/example env file
- document the variable

Do not commit secrets.

## 22.4 Do Not Hide Missing Required Config With Defaults

For mandatory configuration, validate it and fail clearly when absent.

Do not silently use arbitrary fallback values.

## 22.5 Validate Configuration at Startup

Mandatory backend configuration should be validated during startup.

Fail early rather than failing later during feature execution.

---

# 23. Helpers and Utilities

Reusable helpers may live in existing `helpers` or `utils` directories.

However:

- they must be genuinely reusable
- do not create dumping grounds
- domain-specific logic should remain in the domain
- use meaningful names
- do not duplicate existing helpers

Search first before adding a new utility.

---

# 24. Error Handling

## 24.1 Handle Errors Properly

Do not swallow errors, hide failures with arbitrary fallbacks, or expose raw infrastructure errors.

Use existing project error handling.

## 24.2 Backend User-Facing Errors Must Use i18n

Use backend translations for errors intended for frontend display.

## 24.3 Do Not Expose Internal Errors

Never expose stack traces, SQL errors, internal paths, raw third-party errors, or sensitive values to users.

## 24.4 Frontend Must Handle Async States

Every async UI should consider loading, error, empty, and success states.

Avoid silent failures.

---

# 25. Logging

## 25.1 Use NestJS Logger

Backend logging should use NestJS Logger and the project's logging setup.

## 25.2 Logs Must Be Readable and Useful

Include useful non-sensitive context such as operation, entity ID, status, or request/correlation ID.

Avoid vague logs such as "Something failed".

## 25.3 Do Not Log Sensitive Information

Never log passwords, access tokens, refresh tokens, authorization headers, secrets, private keys, or unnecessary personal data.

## 25.4 Remove Frontend Console Logs

Do not leave `console.log(...)` or `console.debug(...)` in committed frontend code.

Temporary debugging logs must be removed.

---

# 26. Security

Follow secure coding practices.

At minimum:

- validate inputs
- parameterize database access
- enforce backend authorization
- protect secrets
- sanitize/encode output appropriately
- prevent injection
- prevent path traversal
- avoid insecure object access
- rate limit sensitive endpoints
- use existing secure authentication
- avoid exposing internal details
- keep dependencies maintained

Never rely on frontend security controls alone.

---

# 27. API Design

## 27.1 Use Appropriate HTTP Methods

Follow established semantics:

- GET — retrieve
- POST — create/action
- PATCH — partial update
- PUT — replacement where appropriate
- DELETE — delete

Follow existing project conventions when already defined.

## 27.2 Use Appropriate Status Codes

Do not return successful status codes for failures.

Maintain consistency.

## 27.3 Avoid Unbounded Collection APIs

Use pagination, limits, and filtering where large result sets are possible.

---

# 28. Database Performance

When modifying persistence logic, consider:

- N+1 queries
- missing indexes
- unbounded queries
- unnecessary joins
- unnecessary selected fields
- repeated queries
- transaction boundaries

Do not optimize blindly, but do not introduce obvious performance problems.

---

# 29. Transactions

Use transactions where multiple persistence operations form one atomic business action.

Avoid leaving partially updated data.

Keep transactions short.

Avoid external API calls while holding a transaction open unless explicitly required.

---

# 30. Concurrency and Idempotency

For retryable or concurrent operations, consider duplicate requests, race conditions, idempotency, database constraints, atomic updates, queue retries, and webhook retries.

Do not rely only on "check then update" when concurrency can violate the invariant.

---

# 31. TypeScript

## 31.1 Avoid `any`

Do not use `any` merely to silence compiler errors.

Prefer accurate types.

If the type is genuinely unknown, use `unknown` and narrow it safely.

## 31.2 Avoid Unsafe Casts

Do not use `value as SomeType` just to bypass type checking.

Prefer type guards, DTO validation, schema validation, or accurate interfaces.

## 31.3 Avoid `@ts-ignore`

Fix the typing problem instead of suppressing it unless there is a documented technical reason.

---

# 32. Accessibility

Frontend changes must preserve accessibility.

At minimum:

- use semantic elements
- label inputs
- support keyboard usage
- provide accessible button names
- preserve focus behavior
- provide meaningful alt text
- do not communicate meaning only through color

---

# 33. README and Documentation

## 33.1 Update README When Developer Usage Changes

Update README files when changes affect environment variables, setup, migration commands, development commands, dependencies, configuration, deployment requirements, or architecture developers need to understand.

## 33.2 Do Not Update README for Trivial Internal Changes

Avoid unnecessary documentation noise.

---

# 34. Comments

Use comments only when they improve understanding.

Good comments explain:

- why an unusual decision exists
- external limitations
- compatibility constraints
- non-obvious business rules

Avoid obvious comments.

Do not leave outdated comments, misleading comments, or commented-out code.

---

# 35. File and Directory Structure

Maintain the existing project directory structure.

Do not randomly create top-level directories.

Before adding files, inspect where equivalent files already live.

Keep:

- DTOs with DTOs
- entities with entities
- hooks with hooks
- endpoints under `api/endpoints`
- services in service structure
- components according to local/global convention
- helpers in existing helper/utility structure

---

# 36. Do Not Introduce Duplicate Architecture

Do not add another HTTP client, fetcher, state-management library, permission system, logging system, date/time mechanism, styling system, or UI component library without explicit approval or strong technical justification.

Use the existing stack.

---

# 37. Testing

Add tests for important new behavior where appropriate.

Prioritize:

- business rules
- validations
- permissions
- state transitions
- service logic
- error handling
- persistence behavior
- critical frontend behavior

Bug fixes should include regression tests when practical.

Do not disable tests merely to make changes pass.

---

# 38. Dependencies

Before adding a dependency:

1. check whether the project already has a solution
2. check whether the framework already provides it
3. evaluate maintenance impact
4. evaluate security impact

Do not add dependencies for trivial functionality.

---

# 39. Definition of Done

Before completing a task, verify:

## General

- [ ] Existing patterns were inspected.
- [ ] Code is readable.
- [ ] Names are meaningful.
- [ ] Functions are focused.
- [ ] No unnecessary fallbacks were added.
- [ ] Existing utilities/components were reused where appropriate.

## i18n

- [ ] No user-facing text is hardcoded.
- [ ] Translation keys exist.
- [ ] No i18n default values were added.
- [ ] Backend user-facing errors use i18n.

## Backend

- [ ] Controllers remain thin.
- [ ] Services contain business logic.
- [ ] DTO validation is used appropriately.
- [ ] Backend validation exists.
- [ ] Permission checks are correct.
- [ ] Existing rate limiting is used where needed.
- [ ] NestJS Logger is used.
- [ ] Sensitive values are not logged.

## Database

- [ ] Entity conventions are followed.
- [ ] Entity is registered correctly.
- [ ] Migration exists where required.
- [ ] Migration was generated and reviewed.
- [ ] Applied migrations were not modified.
- [ ] Transactions/invariants were considered.
- [ ] Query performance was considered.

## Frontend

- [ ] Endpoints are centralized.
- [ ] Existing fetcher is used.
- [ ] Existing service pattern is used.
- [ ] TanStack Query is used for server state.
- [ ] Cache invalidation/update is correct.
- [ ] Existing components are reused.
- [ ] Layouts are reused.
- [ ] Routes follow existing patterns.
- [ ] Tailwind/theme styling conventions are followed.
- [ ] Colors are not hardcoded unnecessarily.
- [ ] Mobile responsiveness is maintained.
- [ ] Accessibility is considered.
- [ ] Console logs are removed.

## Configuration

- [ ] Configurable values use project configuration.
- [ ] Mandatory configuration is validated.
- [ ] Development/example env files are updated where needed.
- [ ] No secrets are committed.
- [ ] Arbitrary config fallbacks are not introduced.

## Time

- [ ] Absolute timestamps follow UTC epoch conventions.
- [ ] Timezone-aware behavior uses the existing timezone mechanism.
- [ ] Date-only values are handled correctly.

## Documentation

- [ ] README was updated if developer setup/config changed.

## Security

- [ ] Backend authorization is enforced.
- [ ] Inputs are validated.
- [ ] Secrets are protected.
- [ ] Security controls were not bypassed.
- [ ] Sensitive data is not exposed.

## Tests

- [ ] New important behavior is tested.
- [ ] Edge cases are tested.
- [ ] Bug fixes have regression tests where practical.
- [ ] Existing tests remain passing.

---

# 40. Priority When Rules Conflict

Use this priority:

1. Correctness
2. Security
3. Data integrity
4. Business requirements
5. Authorization
6. Maintainability
7. Readability
8. Existing project consistency
9. Testability
10. Reusability
11. Performance where relevant
12. Conciseness

Do not follow a style rule if it makes the implementation incorrect or insecure.

---

# 41. Final Rule

Before adding anything new, ask:

- Does this already exist?
- Is there already a project pattern?
- Is this in the correct layer?
- Does this need i18n?
- Does this need backend validation?
- Does this need permission checks?
- Does this need a migration?
- Does this need configuration?
- Does this need tests?
- Can an existing component be used?
- Can an existing hook/service/helper be used?
- Is this readable?
- Am I masking a bug with a fallback?
- Am I introducing a second architecture for something already solved?
- Will another developer understand this quickly?

Prefer extending the existing architecture cleanly over introducing another pattern.
